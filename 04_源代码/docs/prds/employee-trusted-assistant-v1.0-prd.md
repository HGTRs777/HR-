# 员工可信制度助手增量重构 - 产品需求文档（PRD）

## 需求描述

### 背景

- **业务问题**：员工端已有问答、证据、情景条件、清单、版本刷新和意见闭环，但页面层级平均、员工术语偏技术化、回答与办理之间缺少明确的视觉主线。
- **目标用户**：使用实名账号查询和办理 HR 制度事项的非技术员工。
- **价值主张**：在不重建业务系统的前提下，把现有能力组织成“问答 → 条件 → 判断 → 清单 → 依据 → 反馈”的可信办理体验。

### 功能边界

- 保留现有 Vue 页面、`/api/v1/*` 接口风格、会话/回答/证据/反馈模型。
- 不新增第二套情景、清单、证据或反馈系统。
- 不展示模型隐藏推理，不制造员工档案和业务流程。
- 仅在现有反馈类型与版本展示字段不足时扩展现有接口；不新增数据库表。

## 代码审计结论

### A. 可直接复用

- 会话：`Conversation.scenario_state`、消息、回答均按实名员工映射的 `employee-{id}` 隔离；已有新建、查询、切换、删除接口。
- 多轮问答：`submit_question()` 复用最近消息，追问继续使用当前 `conversation_id`。
- 条件推演：`scenario`、`scenario_form`、`clarification`、`replay_answer()` 和 `scenario_changes` 已完整存在。
- 办理数据：`Answer.action_card/checklist` 已包含适用条件及带证据 ID 的时间、材料、注意事项；复测会创建新的回答并保留来源回答。
- 证据：Claim 与 Evidence 具有稳定锚点、制度/版本/生效日期，可通过现有 Reader 定位原文。
- 制度更新：知识指纹和启用版本共同计算 `stale`；现有 refresh 接口保留旧回答并创建新回答。
- 意见：反馈自动关联 answer、conversation、制度快照；实名由服务端账号决定；事件表已记录处理时间线。
- 容错：会话、意见、原文读取已有局部 try/catch；登录后并发加载的两项彼此独立，需改为独立容错。

### B. 存在但需调整

- 页面实际为“侧栏 + 两列”，视觉上三栏同权，且右侧仍使用“情景沙盘”技术术语。
- Hero 高度偏大；常问问题仅有三个静态按钮，聊天输入不够突出。
- 回答摘要、条件、清单、覆盖率、证据虽齐全，但缺少“结论/与你相关/依据/下一步”的员工层级。
- 清单完成状态仅存在前端内存并按 `answer_id` 隔离；切换会话可恢复，但条件重放产生新 answer 时不会迁移相同事项的勾选状态，也无覆盖提示。
- 意见时间线直接显示底层 action 枚举；表单为 Select，不够直观。
- 移动端把三栏顺序堆叠，尚未使用 Drawer/折叠入口。

### C. 真正需要新增

- 在现有 action card 上计算百分比、下一未完成项、全完成状态，并在重放后迁移同名事项完成状态。
- 条件变化前的进度保护提示；重放成功后的“清单已重新生成”反馈。
- 回答快捷操作与轻量评价入口，继续复用现有反馈表。
- 中文反馈事件时间线和意见类型选择卡。
- 回答序列化增加可验证的旧版/当前启用版本摘要，供制度更新卡展示；无需数据库迁移。
- 桌面/移动端入口和 Playwright 核心流程覆盖。

### 审计发现的可信性问题

- 当前前端 `checklistTemplates` 根据事项硬编码审批步骤，会产生制度未必支持的流程；应移除，改用后端已有、带证据的 action card 步骤。
- 当前前端用固定天数自行计算“预计完成日期”，并非后端或制度计算；不得继续作为精确预测展示。仅当接口以后提供可靠日期时显示，现阶段导出也不声称预计日期。
- 当前“证据覆盖率 100%”面向员工过于技术化；底层数值保留，员工端转换为可信度、依据数量和验证状态。

## 设计与技术决策

- **布局**：桌面保持历史窄侧栏 + 主聊天 + 辅助办理栏；聊天权重最大。移动端聊天为主，历史和办理助手使用 Drawer。
- **状态**：不增加全局状态库；在当前页面按 answer/conversation 键保存 UI 完成状态，重放时按稳定的事项内容迁移。
- **API**：沿用 chat/replay/refresh/reader/feedback；仅扩充 answer 的 `policy_updates` 和现有反馈类型，不新增路由。
- **数据模型**：现有 JSON/字符串字段足够，不新增表、不迁移数据库。
- **推荐追问**：空态沿用现有常问入口；回答后仅根据当前真实事项/制度生成少量上下文入口，仍调用同一个 submitQuestion。
- **动效**：150–250ms 收放、卡片 2px hover、清单进度自然更新；遵守 reduced-motion。

## 验收标准

- [ ] 历史栏桌面默认展开，可无刷新收起/展开，且当前输入、会话、条件和清单状态不丢失。
- [ ] 中间聊天成为最大视觉区域；移动端无横向溢出，并可通过 Drawer 访问历史与办理助手。
- [ ] 回答按真实数据展示结论、已确认条件、制度依据和动态下一步；无空壳模块和隐藏思维过程。
- [ ] 右侧统一称“我的情况与办理助手”，支持无需条件、待补充、已确认三种状态。
- [ ] 只使用现有 action card/checklist，进度、百分比、下一步、完成状态和流程详情正确。
- [ ] 条件变化会提示清单更新；新回答保留相同事项勾选状态，不静默覆盖。
- [ ] 制度过期回答显示旧版本、当前版本和重新回答入口；历史回答不被改写。
- [ ] 员工端显示可信度/依据数/验证状态，不暴露检索内部评分。
- [ ] 回答问题反馈自动关联当前回答；意见中心显示自然中文事件时间线。
- [ ] 会话、意见、辅助读取接口独立容错。
- [ ] TypeScript strict、Vitest、Pytest、生产构建及桌面/移动 Playwright 通过，Console 无新增错误。

## 分阶段实施

1. 重排三栏和紧凑 Hero，补充桌面/移动导航与局部状态。
2. 结构化回答、三态条件助手、真实 action card 清单进度与重放迁移。
3. 版本更新卡、可信度表达、上下文追问和快捷操作。
4. 轻量评价、意见选择卡、中文时间线与独立容错。
5. 补齐单元/E2E/API 测试并执行全量验证。
