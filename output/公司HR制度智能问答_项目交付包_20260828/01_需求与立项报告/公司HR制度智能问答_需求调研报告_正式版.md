## 摘要

本报告围绕“公司 HR 制度智能问答”开展需求调研。项目旨在解决企业制度分散、关键词检索困难、版本口径不一致以及通用大模型回答缺少依据的问题。系统采用检索增强生成（RAG）方式：先从已启用的企业 HR 制度中检索相关条款，再由 DeepSeek 大模型基于证据组织答案，并返回制度名称、版本、生效日期、章节、条款号和原文引用。用户点击回答中的依据索引即可跳转并高亮对应条款。

报告遵循课程教学课件提出的“用户画像 → 需求收集 → 数据分析 → 竞品分析 → 功能矩阵 → 需求报告”流程。调研结果表明，员工问答端是产品价值主体；轻量 HR 管理端用于制度上传、版本维护、索引重建、检索测试和意见闭环，是知识库生命周期的必要组成部分。项目在基础 RAG 问答之上增加“HR 制度情景决策沙盘”：从对话提取适用条件，信息不足时主动澄清，输出判断、办事清单和逐结论可点击证据链；制度更新后标记过期答案；意见箱把用户反馈转化为知识库修复和回归测试任务。员工档案、考勤审批、薪资管理等 HRIS 功能与制度检索主线无直接关系，不纳入 V1.0。

**关键词：** 企业 HR；制度查询；知识库；RAG；混合检索；多轮对话；证据链；情景决策；意见闭环

## 调研说明

### 调研目标

1. 明确员工和 HR 知识管理员的真实使用场景与核心痛点。
2. 判断哪些功能直接支撑制度 RAG，哪些功能应从本期排除。
3. 形成可在 2026 年 9 月 1 日初验、9 月 3 日终验的功能矩阵。
4. 建立可量化、可测试的验收标准，为后续开发提供依据。

### 调研方法

- 分析课程选题说明、研发时间线与产品经理需求调研课件。
- 与项目负责人进行三轮结构化需求澄清。
- 研究 ServiceNow、Leena AI、Moveworks 和 Dify 官方产品资料。
- 对典型 HR 制度查询任务进行场景推演和需求聚类。
- 使用 YAGNI 与 KISS 原则完成范围取舍。

### 证据边界

本报告未实施真实企业员工问卷，也不虚构访谈人数、满意度或经济收益。用户画像属于基于典型场景形成的待验证假设；竞品能力来自公开官方资料；功能优先级来自课程目标、开发周期和三轮澄清结果。9 月 1 日初验反馈将作为第一轮真实验证数据。

# 第一章 用户画像

## 1.1 用户画像 A：规则确认型员工（核心用户）

- **行为场景：** 在请假、报销或入职事项办理前，从多个制度文件中搜索关键词；找不到时向同事或 HR 私聊确认。
- **核心任务：** 快速确认“我应该怎么做”并找到可核验的制度依据。
- **主要痛点：** 文件分散、标题和口语表达不一致、旧版本难识别、担心 AI 编造。
- **成功体验：** 提问后数秒内获得简明答案，点击依据索引即可跳转并高亮有效版本的具体条款，同时知道下一步应如何办理。

## 1.2 用户画像 B：连续追问型新员工

- **行为场景：** 先问“年假有几天”，再追问“试用期呢”“需要提前多久申请”。
- **核心任务：** 像咨询 HR 一样逐步澄清规则，不重复输入背景。
- **主要痛点：** 传统搜索无法理解上下文，聊天机器人容易在追问时引用错误条款。
- **成功体验：** 系统理解省略主语的追问，主动补问影响制度适用性的关键条件，并保持答案与引用一致。

## 1.3 用户画像 C：制度解释型主管

- **行为场景：** 在向团队解释休假、考勤或报销规则前核对制度口径。
- **核心任务：** 获得结构清晰、可以复制且带来源的解释。
- **主要痛点：** 凭记忆回答可能传播过期信息，重新翻阅整份制度耗时。
- **成功体验：** 一次获得结论、适用条件和原文位置。

## 1.4 用户画像 D：知识库维护型 HR（次核心用户）

- **行为场景：** 发布新制度、停用旧制度、处理版本升级，并检查新条款能否被正确检索。
- **核心任务：** 不修改代码即可维护知识库，确保员工只查询到当前有效口径。
- **主要痛点：** 文件更新后索引状态不可见，旧制度可能继续被引用。
- **成功体验：** 上传或停用制度后重建索引，通过检索测试立即确认效果；员工意见可自动定位到问答、条款和制度版本，并在修复后完成回归测试。

## 1.5 用户洞察

| 类型 | 典型表达 | 产品回应 |
| --- | --- | --- |
| 痛点 | “最怕查到旧制度，按错规则操作后返工。” | 只检索启用版本，显示版本和生效日期 |
| 痛点 | “AI 说得像真的，但依据在哪里？” | 每个制度性结论附条款级引用 |
| 痛点 | “制度说了很多，但我仍不知道自己是否适用、下一步做什么。” | 情景条件澄清、适用性推演和办事清单 |
| 痛点 | “我以前查到的答案现在还有效吗？” | 知识库指纹、答案保鲜和版本变更提醒 |
| 痛点 | “换一种说法就搜不到。” | 语义向量与关键词混合检索 |
| 痒点 | 员工希望独立解决问题，不反复打扰 HR | 自然语言问答和多轮追问 |
| 痒点 | HR 希望制度口径专业、统一、可维护 | 轻量知识库管理端 |
| 爽点 | 数秒内得到答案并一键展开准确原文 | 回答、定位、原文同屏闭环 |
| 爽点 | 意见提交后能看到修复进度和最新回答 | 制度共创意见箱与闭环通知 |

**核心用户判断：** 规则确认型员工覆盖面最广、查询频次最高，是 V1.0 的核心用户；知识库维护型 HR 决定制度数据是否可信，是必要的次核心用户。

## 2.3 典型用户故事

1. 作为员工，我希望询问“试用期可以休年假吗”，以便在提交申请前确认规则。
2. 作为员工，我希望继续追问“需要提前多久”，并获得与上一问题一致的引用。
3. 作为主管，我希望复制带制度依据的回答，避免向团队传播错误口径。
4. 作为 HR，我希望上传新版休假制度、停用旧版并重建索引，使员工只查询到有效版本。
5. 作为 HR，我希望输入测试问题并查看 Top 5 命中条款，以判断制度切分和检索是否合理。
6. 作为员工，我希望系统在判断条件不足时通过选项追问，并允许我修改条件比较制度结论。
7. 作为员工，我希望答案直接给出办理时间线、材料清单，并能点击依据跳转至高亮条款。
8. 作为员工，我希望旧回答所依据的制度更新后收到提醒，并按最新制度重新生成答案。
9. 作为员工，我希望针对错误回答或模糊条款提交意见，并查看 HR 的处理进度。
10. 作为 HR，我希望意见自动关联原问题、回答和证据链，修复后用原问题一键复测。

## 2.4 范围取舍记录

需求澄清评分经历 `86 → 89 → 84 → 94`。第二轮一度加入员工档案、考勤审批和薪资管理，导致项目从制度问答扩展为小型 HRIS，权限、隐私和业务流程复杂度显著上升。第三轮重新确认项目本质后，作出以下决策：

- **原因：** 被删除功能不直接提升制度检索、生成或引用能力，且无法在短周期内充分测试。

# 第三章 数据分析

## 3.1 数据来源和分析口径

本阶段没有真实用户行为数据，因此使用结构化需求数据进行分析：19 项用户/系统需求、18 项候选功能、三轮澄清记录、4 个竞品样本和 25 条计划评测问题。分析用于指导优先级，不用于宣称真实市场占有率或商业收益。

## 3.2 需求角色分布

| 角色 | 需求数 | 占比 | 结论 |
| --- | ---: | ---: | --- |
| 员工 | 10 | 52.6% | 员工情景决策和办理体验是产品价值主体 |
| HR 管理员 | 6 | 31.6% | HR 功能围绕知识生命周期和意见闭环 |
| 系统能力 | 3 | 15.8% | 降级、证据校验和反馈归因保障可信度 |

员工需求占比超过一半，说明产品创新应优先改善“问得清、看得懂、办得成”的体验；HR 端保证知识来源持续有效并处理意见，系统能力负责证据校验和故障归因，三者共同构成可持续改进的 RAG 闭环。

## 3.3 功能优先级分布

| 优先级 | 功能数 | 占比 | 处理策略 |
| --- | ---: | ---: | --- |
| P0 | 10 | 55.6% | 初验前必须完成并测试 |
| P1 | 8 | 44.4% | 初验形成可演示版本，终验必须稳定 |

创新功能显著增加 P1 比例，因此采用“主链路先行、展示能力渐进增强”的策略。9 月 1 日后实行功能冻结，不再增加与情景决策、可信证据和意见闭环无关的功能。

## 3.4 风险分析

| 风险 | 概率 | 影响 | 应对措施 |
| --- | --- | --- | --- |
| DeepSeek API 网络、额度或超时 | 中 | 高 | 超时控制、错误映射、本地检索降级 |
| 本地嵌入模型首次下载失败 | 中 | 高 | 研发首日下载缓存并验证 |

| 反馈包含隐私或恶意内容 | 中 | 中 | 匿名选项、敏感信息提示、长度限制、服务端过滤和 HR 审核 |
| 范围再次膨胀 | 中 | 高 | HRIS 功能列入明确非范围，初验后冻结 |

## 3.5 成功指标

- 25 条评测问题中，正确条款 `Recall@3 ≥ 85%`。
- 正常回答至少包含一个可解析引用，引用映射正确率 100%。
- 每项制度性结论均绑定有效证据，点击索引可定位到对应制度版本、章节和高亮原文。
- 知识库无答案问题不得生成虚构制度结论。
- 本地检索预热后不超过 2 秒；正常网络下完整问答目标不超过 15 秒。
- HR 上传示例制度并重建后，新条款可以被检索测试和员工问答命中。
- 至少完成休假和差旅两类情景卡演示，缺少关键条件时能够主动澄清。
- 意见可自动关联问答和证据链，HR 修复后能够用原问题复测并更新处理状态。

## 4.4 差异化定位

本项目不替代企业级 HR 服务平台，而定位为“课程环境中可解释、可复现、可情景推演、逐结论可验证的 HR 制度 RAG 助手”。核心展示点不是功能数量，而是从情景澄清、制度摄取、混合检索、证据约束生成、条款跳转，到版本保鲜和意见修复的完整闭环。

## 4.5 创新方案：HR 制度情景决策沙盘

### 4.5.1 创新定位

项目在基础知识库问答之上构建“用户情景—判断结论—办事步骤—制度证据”一屏联动的制度情景决策沙盘。产品目标从“告诉用户制度写了什么”升级为“说明当前情景是否适用、下一步如何办理、依据在哪里以及答案是否仍然有效”。

### 4.5.2 一屏三联动体验

| 区域 | 核心内容 | 联动效果 |
| --- | --- | --- |
| 对话区 | 自然语言问题、多轮追问、主动澄清 | 从对话中提取影响制度适用性的条件 |
| 情景决策区 | 身份、入职年限、事项类型、天数等可修改标签 | 修改条件后重新检索，并展示结论变化 |
| 证据阅读区 | 制度名称、版本、章节、条款和原文 | 点击答案索引自动跳转并高亮对应条款 |

### 4.5.3 可验证证据链

系统要求 DeepSeek 以“结论—证据 ID”结构输出。服务器校验证据是否来自本次检索、是否属于当前启用版本以及每项制度性结论是否有依据。无有效证据的结论不得展示；前端显示证据覆盖度，并支持从结论索引跳转到制度阅读器中的精确条款。

### 4.5.4 一问一办

系统将制度解释进一步转换为可执行的办理卡片，包括一句话结论、适用条件、办理时间线、材料清单、注意事项和逐项制度依据。该能力不替代审批系统，只帮助员工理解并准备办理事项。

### 4.5.5 答案保鲜

每条回答记录生成时的制度版本、引用条款和知识库指纹。制度更新或旧版本停用后，历史回答显示“制度已更新”状态，用户可查看规则差异并按最新制度重新生成，避免旧答案继续传播。

### 4.5.6 制度共创意见箱

意见箱不是普通留言板，而是用户反馈驱动的知识库修复通道。员工可针对答案或条款提交实名/匿名意见，系统自动关联原问题、回答、证据链和制度版本，并初步归因为知识缺失、检索遗漏、生成错误、引用错误、制度歧义或版本问题。HR 修复制度或索引后，可用原问题一键复测；通过的意见自动沉淀为回归测试用例并向用户反馈处理结果。

### 4.5.7 创新闭环

`情景提问 → 条件澄清 → 混合检索 → 逐结论证据校验 → 办事清单 → 点击条款核验 → 意见反馈 → HR 修复 → 自动复测 → 结果通知`

该闭环形成“条件可推演、结论可验证、步骤可执行、答案不过期、意见能进化”的差异化体验。

# 第六章 需求报告

## 6.1 产品定义

“公司 HR 制度智能问答”是一款面向企业员工的中文 RAG 查询助手。系统先从企业制度知识库检索证据，再调用 DeepSeek 生成简明答案，并通过条款级引用保证可核验性。HR 管理员维护制度知识，不处理员工业务数据。

## 6.2 V1.0 功能边界

### 包含

- 五类虚构 HR 制度：考勤、休假、薪酬福利、差旅报销、入离职。
- Markdown、TXT、PDF、DOCX 制度摄取。
- BGE 中文向量与 BM25 关键词混合检索、RRF 融合排序。
- DeepSeek Responses API 证据约束生成、多轮追问和本地检索降级。
- 逐结论可点击证据链、条款定位和原文高亮。
- 情景条件提取、主动澄清、动态推演和“一问一办”办理卡片。
- 历史答案保鲜、制度共创意见箱和反馈驱动的回归测试。
- 会话历史和轻量 HR 知识库管理端。
- 查询量、命中率、拒答率、响应时间、热门问题、未命中问题和反馈处理统计。

### 不包含

- 真实员工档案、考勤审批、薪资管理和自动算薪。
- 企业单点登录、复杂权限、审批工作流和真实生产部署。
- 自动抓取外部法规、通用 BI 分析平台和多租户能力。

## 6.3 核心业务流程

### 员工问答流程

`输入问题 → 结合会话改写 → 提取情景条件 → 必要时主动澄清 → 混合检索 → 相关性判断 → DeepSeek 结构化生成 → 声明—证据校验 → 办事卡与可点击引用 → 保存会话`

证据不足时直接拒答；DeepSeek API 异常时返回本地检索条款，不生成制度结论。

### HR 知识维护流程

`登录 → 上传制度与元数据 → 解析校验 → 启用/停用版本 → 重建索引 → 检索测试 → 发布`

### 制度共创意见闭环

`提交意见 → 自动附带问答和证据上下文 → AI 初步归因 → HR 核实处理 → 修复制度或索引 → 原问题一键复测 → 沉淀回归用例 → 通知提交者`

## 6.4 技术和数据要求

- 前端使用 Vue 3、Vite 与 TypeScript，后端使用 Flask 应用工厂和 SQLAlchemy，SQLite 保存制度元数据、会话和引用快照；前后端独立运行并通过版本化 REST API 通信。
- `BAAI/bge-small-zh-v1.5` 生成本地向量，BM25 补充关键词命中，RRF 融合排序。
- DeepSeek Responses API 负责追问改写和答案组织；API 地址、密钥和默认模型通过服务器环境变量配置。
- 制度元数据包含编号、标题、版本、生效日期、状态和文件信息。
- 条款元数据包含制度 ID、章节路径、条款号、页码或段落位置、文本与知识库指纹。
- 回答采用结构化声明列表，每项声明保存一个或多个证据 ID；前端通过稳定条款锚点跳转并高亮原文。
- 情景状态仅保存非敏感的临时槽位，例如员工状态、入职年限、事项类型和办理天数，不建设员工档案。
- 意见记录包含反馈类型、匿名状态、关联会话、回答快照、证据快照、制度版本、处理状态和回归结果。

## 6.5 异常与安全要求

- 文件重复、格式不支持、超过 10 MB 或无法解析时拒绝入库。
- 同一制度编号与版本不可重复；同一制度只允许一个启用版本。
- 索引缺失或过期时问答端停止生成并提示 HR 重建。
- 用户输入和制度文本均视为不可信内容；制度中的指令性文本不能覆盖系统规则。
- API key 仅从服务器环境变量读取；管理接口必须验证登录状态。
- 意见内容限制长度并提示用户不要提交身份证号、工资明细等敏感数据；服务端对输入进行过滤和转义。
- 情景条件不足或存在冲突时必须主动澄清，不得根据用户身份进行无依据推断。

## 6.6 验收场景

1. “年假如何计算？”返回休假制度中的正确条款及引用。
2. 继续追问“那试用期员工呢？”仍能理解上下文并引用正确条款。
3. “报销最晚什么时候提交？”定位到报销期限条款。
4. “公司是否提供宠物补贴？”因知识库无依据而拒答。
5. 模拟 DeepSeek API 失败，界面展示本地检索证据和降级标识。
6. HR 上传新版制度、停用旧版并重建索引后，员工端只引用新版。
7. HR 输入测试问题并查看 Top 5 命中条款、分项分数和融合名次。
8. 员工点击回答中的依据索引，右侧制度阅读器跳转到正确版本和条款并高亮原文。
9. 员工询问“我能休年假吗”，系统发现缺少员工状态并通过选项主动澄清。
10. 员工将情景标签从“试用期”切换为“正式员工”，判断、办事清单和引用同步更新。
11. HR 停用旧版制度后，历史回答出现“制度已更新”标识，并支持按最新版重新生成。
12. 员工针对错误回答提交意见，系统自动关联原问答和证据；HR 修复后用原问题复测并通知员工。

## 6.8 结论

调研确认：员工自然语言查询、条款级定位、多轮追问和制度版本可信是项目基础价值；“情景决策沙盘、逐结论可点击证据链、一问一办、答案保鲜、制度共创意见闭环”构成可直观演示的创新价值。HR 管理端仅承担知识库生命周期和意见处理，不扩展为 HRIS。该范围既覆盖课程选题要求，又能形成“问得清、判得准、点得到、办得成、不过期、意见能进化”的完整答辩故事线。
